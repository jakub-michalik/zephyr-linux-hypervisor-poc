THE QUESTION

Can Zephyr take over real-time work on an application processor?

VARIANT A · THIS POC

Under a hypervisor

Linux and Zephyr side by side on one SoC, isolated by Xen. Real-time quality measured while Linux is loaded.

VARIANT B

Natively

Zephyr alone on the Cortex-A cores, no Linux. Limits of the MMU, SMP and driver support documented.

VARIANT C

As native_sim

Zephyr compiled as a Linux process for host-side testing and CI. No real-time behaviour.

The posting describes running Zephyr on a feature-rich microprocessor, natively or with a hypervisor, plus native_sim as an option. This PoC starts with the hypervisor variant because it answers the mixed-criticality question directly.

ARCHITECTURE

Two operating systems, one SoC, Xen in between

Dom0 · Debian 13, Linux 6.12

vCPUs pinned to cores 0–2 · management (xl), drivers, load generators, measurement tools

DomU · Zephyr 4.1

rt_probe app · 1 vCPU on core 3 · 16 MB RAM

Xen 4.20 hypervisor · EL2

stage-2 MMU isolation · virtual GICv3 · vCPU pinning · PV console and event channels

ARM64 platform: QEMU virt, 4× Cortex-A72, GICv3 (stand-in for i.MX8M)

Same software stack moves to an i.MX8M Plus / i.MX93 board for real timing numbers

Linux runs as the privileged domain Dom0, Zephyr as an unprivileged guest. Xen sits at exception level 2 and enforces memory isolation with the stage-2 MMU. The platform is emulated in QEMU for now.

BOOT FLOW

How the board boots

1 · QEMU

Loads Xen, the Dom0 kernel and initrd into RAM and passes a device tree

2 · Xen (EL2)

Finds the kernel and initrd as multiboot modules in the device tree

3 · Dom0 Linux

Starts Xen tools: xenstored, xenconsoled, xl

4 · Zephyr DomU

Created by xl from Linux, pinned to its own core

Same flow as on an i.MX board

On i.MX8M, U-Boot takes QEMU’s role: it loads Xen, kernel, initrd and the device tree with the same multiboot nodes, then jumps to Xen. No UEFI or GRUB is needed, which keeps the boot chain short and predictable.

Patching the device tree with xen,xen-bootargs and multiboot module nodes is exactly what U-Boot scripts or Xen ImageBuilder do on real boards.

CPU PARTITIONING

Two placements are compared

DEDICATED CORE

Zephyr alone on core 3

Dom0 has 3 vCPUs pinned to cores 0–2 (dom0_vcpus_pin). Zephyr’s vCPU is pinned to core 3. Nothing else is scheduled there.

cpus="3"

SHARED CORE

Zephyr shares core 0 with Linux

Zephyr’s vCPU is pinned to core 0, where a Dom0 vCPU also runs. The Xen credit2 scheduler decides who runs when.

cpus="0"

Xen 4.20, credit2 scheduler, 4 physical cores, Dom0 1 GB RAM, Zephyr 16 MB RAM.

Dedicated cores are the usual choice for real-time guests. The shared case shows what happens when you consolidate without partitioning.

DEMO APPLICATION

rt_probe: a real-time task that measures itself

Periodic RT task

Highest-priority thread wakes every 1 ms and records how late it was versus the ideal schedule. Min, average, max and a histogram are reported every second.

Command channel

Linux talks to Zephyr over the Xen PV console: PING for round-trip latency, FAULT to crash Zephyr on purpose, PERIOD to change the task rate.

BOOT uptime_ms=3 timer_hz=62500000
STAT t=12 n=1000 period_us=1000
  min_us=4 avg_us=31 max_us=412
  overruns=0 hist=410,520,61,9,0,0
PONG 17

Machine-readable output, parsed by the Linux-side scripts. Values above illustrate the format only.

The STAT line in the code block shows the output format, not a measured result. Real numbers appear on the results slides once runs complete.

rtprobe.py

Talks to Zephyr over its PV console. Starts the domain, records latency, measures round trips, boot time and crash recovery.

run_scenarios.sh

Runs all scenarios with stress-ng load and cyclictest on Linux in parallel, so Zephyr and Linux latency are measured side by side.

The same scripts run unchanged on a real board. Only the timing numbers will differ.

Avg late is how late the 1 ms task woke compared to its ideal schedule. On a shared core, the credit2 scheduler gives Linux time slices of up to about 10 ms, which is exactly the maximum lateness we see. Max values on the dedicated core come from the emulator itself and are expected to be far lower on hardware.

CONTROL EXPERIMENT

The rare misses come from the emulator, not from Xen

Setup (same emulator, same rt_probe)Missed periodsMax late
Zephyr alone, no Xen, no Linux (33 s)77.3 ms
Xen, dedicated core, Linux idle (30 s)11.3 ms
Xen, dedicated core, Linux CPU stress (30 s)63.6 ms
Xen, dedicated core, Linux memory stress (30 s)73.2 ms

On a dedicated core, Xen adds no visible disturbance. Hard real-time guarantees still need hardware: long worst-case runs and GPIO timing on an oscilloscope.

Each emulated CPU is an ordinary thread on a non-real-time host, so the host can pause it at any time while the clock keeps running. That shows up as lateness even with no hypervisor at all.

KEY FINDING

Under Linux load, a shared core misses 89% of Zephyr’s 1 ms deadlines. A dedicated core misses 0.02%.

Consolidating Linux and Zephyr on one SoC works only with strict CPU partitioning. The hypervisor’s scheduler, not Zephyr, decides real-time quality.

This is the main architectural takeaway: pin the real-time guest to its own core, or use a static partitioning hypervisor such as Jailhouse, or Xen’s null scheduler in a separate cpupool.

Fast start, working channel, clean recovery

Median from unpausing the domain to Zephyr’s first output. 0.82 s including domain creation by xl.

Median round trip over the PV console, no loss. Same under CPU load (1.8 ms); p99 15–19 ms.

FAULT ISOLATION

1.55 s

Crash detected in 0.2 s, Zephyr restarted in 1.35 s. Linux kept running.

Emulated platform: times show the mechanisms work end to end, not real hardware speed.

The PV console is a debug-grade channel; its p99 shows why a production design would use shared memory with event channels instead.

FAULT HANDLING

A Zephyr crash is detected and recovered by Linux

1

Zephyr fails

Fatal error handler calls the Xen hypercall SCHEDOP_shutdown with reason “crash”.

2

Xen marks it

The domain enters the crashed state. Its core and memory stay isolated from Linux.

3

Linux detects

A supervisor in Dom0 sees the state change (about 0.2 s in the emulator).

4

Restart

The domain is destroyed and recreated; Zephyr is back in about 1.4 s.

Linux uptime continues across the test: the crash never reaches Dom0.

Without the hypercall, a crashed Zephyr would just spin and Xen would see a healthy running domain. Reporting the crash makes recovery possible. A watchdog would cover hangs the same way.

FINDING ON THE WAY

The emulator, not Xen, froze the board

SYMPTOM

As soon as any Zephyr guest started, Dom0, SSH and even the Xen console stopped responding.

DIAGNOSIS

Domain creation worked when paused; the freeze came on unpause, also with a stock Zephyr sample. QEMU’s main thread sat at 100% while all virtual CPUs idled.

FIX

QEMU 7.0 shipped with the Zephyr SDK replaced by QEMU 8.2. Everything ran on the first try.

Lesson: pin and document tool versions; an emulator bug can look like a hypervisor bug.

Isolating the cause took three steps: paused versus running domain, own app versus stock sample, then a different emulator version.

KNOWN LIMITS

What this setup can and cannot show

Shows

The architecture works end to end: build, boot, isolation, restart, measurement tooling. Relative effects, such as dedicated versus shared core.

Does not show

Absolute latency. QEMU emulates the CPU in software, so microsecond numbers need the real i.MX board.

The emulated platform proves the method and the integration. Real timing numbers, cache and memory interference, and a Jailhouse comparison require hardware.
